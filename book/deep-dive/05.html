Bagian IV — Dart dan Flutter untuk Aplikasi Mobile

24. Dart: tipe, null safety, collection, class

Dart adalah bahasa yang digunakan Flutter. Dart memakai sound null safety: variabel secara default tidak menerima null; tambahkan ? bila null memang keadaan yang sah. Gunakan final untuk variabel yang tidak diganti, const untuk nilai konstan waktu kompilasi, late hanya bila alasan inisialisasi tertunda jelas. Tipe umum: int, double, num, String, bool, List<T>, Set<T>, Map<K,V>. Pelajari if, for, functions, class, enum, nullable types, dan generic.

class Item {
  final String id;
  final String nama;
  final int jumlah;
  final bool selesai;

  const Item({
    required this.id,
    required this.nama,
    required this.jumlah,
    this.selesai = false,
  });

  Item copyWith({String? nama, int? jumlah, bool? selesai}) => Item(
    id: id,
    nama: nama ?? this.nama,
    jumlah: jumlah ?? this.jumlah,
    selesai: selesai ?? this.selesai,
  );
}

void main() {
  final item = Item(id: 'a1', nama: 'Air', jumlah: 6);
  print(item.copyWith(selesai: true).selesai); // true
}

copyWith adalah pola menghasilkan object baru; pada contoh sederhana ia tidak memungkinkan mengubah field nullable menjadi null melalui parameter biasa. Untuk model dengan field nullable yang kompleks gunakan mekanisme sentinel/generator bila diperlukan. Pelajaran penting: tipe compile-time memperkecil kesalahan, tetapi JSON dari internet tetap harus divalidasi ketika diubah menjadi object.

Praktik: tulis versi Dart dari fungsi kasir dan kebutuhan item. Buat List<Item>, filter selesai, jumlahkan stok, urut berdasarkan nama. Uji item kosong dan nilai negatif. Tes keluar: mampu menjelaskan kapan memakai String? dibanding String.

25. Future, async/await, error, dan Stream

Future<T> merepresentasikan pekerjaan asinkron tunggal, Stream<T> urutan peristiwa dari waktu ke waktu. Panggilan HTTP mengembalikan Future. Tangani try/catch, berikan timeout, dan bedakan error jaringan, parsing, autentikasi, dan server. Jangan menelan exception dengan catch (_) {} tanpa logging atau aksi yang jelas. Hindari memperbarui UI setelah widget dispose; gunakan mekanisme lifecycle sesuai arsitektur.

Future<String> ambilNama() async {
  await Future<void>.delayed(const Duration(milliseconds: 100));
  return 'Checklist siap';
}

Future<void> main() async {
  try {
    final hasil = await ambilNama();
    print(hasil);
  } catch (error) {
    print('Gagal memuat: $error');
  }
}

Praktik: buat simulasi API yang kadang sukses, timeout, dan error; tampilkan state loading/ready/failed dan kemampuan retry terbatas. Tes keluar: tahu mengapa Future tidak berarti tugas dijalankan thread baru secara otomatis.

26. Dasar Flutter: widget tree, state, layout

Flutter membangun antarmuka dari widget. MaterialApp mengatur aplikasi, Scaffold struktur layar, Column/Row layout, Expanded membagi ruang, ListView untuk konten gulir, TextField menerima input, ElevatedButton untuk tindakan. StatelessWidget tampilan berdasarkan konfigurasi; StatefulWidget mempunyai lifecycle dan state lokal. Untuk UI kompleks, pindahkan aturan bisnis ke ViewModel/Controller, bukan memenuhi metode build() dengan HTTP dan SQL.

import 'package:flutter/material.dart';

void main() => runApp(const ChecklistApp());

class ChecklistApp extends StatelessWidget {
  const ChecklistApp({super.key});

  @override
  Widget build(BuildContext context) => MaterialApp(
    debugShowCheckedModeBanner: false,
    home: Scaffold(
      appBar: AppBar(title: const Text('Belajar Flutter')),
      body: const Center(child: Text('Halo, Flutter!')),
    ),
  );
}

Praktik: halaman daftar item dengan AppBar, cards, floating button untuk tambah, halaman detail, dialog konfirmasi hapus. Gunakan theme untuk warna/typography, bukan mengulang style di semua widget. Tes keluar: UI tidak overflow pada layar sempit dan ketika ukuran teks sistem diperbesar.

27. Navigation, form, validasi, dan state management

Navigasi adalah perpindahan antar layar beserta parameter dan pengelolaan riwayat. Untuk aplikasi bertumbuh, pertimbangkan go_router sebagaimana rekomendasi dokumentasi Flutter; untuk latihan awal Navigator bawaan cukup. Form memakai Form, GlobalKey<FormState>, TextFormField, validator, dan pengendalian state. Jangan menaruh input password/token di log. Cegah double submit dengan status loading dan penonaktifan tombol.

State: ephemeral/local state seperti tab terpilih dapat menggunakan setState; application state seperti sesi user dan daftar tersinkron sebaiknya disimpan di ViewModel/repository sesuai skala. Riverpod, Bloc, Provider adalah opsi yang berbeda, bukan tingkatan wajib. Buku ini menggunakan konsep MVVM dan ChangeNotifier pada tahap dasar; library eksternal dipilih setelah kebutuhan nyata jelas. Dependency injection dapat sederhana: kirim repository lewat constructor.

Praktik: form tambah item: nama minimal 2 karakter, jumlah nonnegatif, kategori wajib, tombol disabled saat menyimpan, tampilkan error dekat field. Tulis langkah pengguna dari isi form sampai sukses dan gagal. Tes keluar: penekanan tombol dua kali tidak membuat item duplikat.

28. Arsitektur Flutter: View → ViewModel → Repository → Service

Dokumentasi Flutter menganjurkan pemisahan UI layer (View, ViewModel) dan Data layer (Repository, Service) agar logic dapat diuji dan dikembangkan. View menampilkan data dan memanggil command; ViewModel menyiapkan state UI; Repository menjadi sumber kebenaran data dan mengatur cache/fallback; Service melakukan HTTP, file, atau akses sistem. Tambahkan domain/use-case layer hanya bila aturan bisnis menjadi kompleks; jangan membuat banyak abstraction tanpa manfaat.

lib/
  main.dart
  app/
    app.dart
  features/
    items/
      data/
        item_api_service.dart
        item_repository.dart
      domain/
        item.dart
      presentation/
        items_screen.dart
        items_view_model.dart
  shared/
    network/
    ui/

Alur satu arah: pengguna tekan Simpan → View memanggil ViewModel → ViewModel memanggil Repository → Repository memanggil Service HTTP → server validasi & simpan → Repository memperbarui source of truth → ViewModel memberi state baru → UI merender. Perhatikan otorisasi selalu diverifikasi di server, bukan cukup dengan menyembunyikan fitur di Flutter.

Praktik: buat FakeItemRepository untuk test dan ApiItemRepository untuk jaringan. Tukar dependency tanpa mengubah layar. Tes keluar: dapat menulis unit test ViewModel tanpa menjalankan server.

29. Integrasi REST API dari Flutter

HTTP request memakai base URL dari environment build/config, bukan password yang ditanam di aplikasi. localhost pada emulator Android menunjuk perangkat emulator, bukan selalu laptop host; untuk Android Emulator biasanya host machine dapat diakses melalui 10.0.2.2, sementara perangkat fisik butuh alamat server yang dapat dijangkau. Verifikasi kebutuhan jaringan pada platform yang dipakai. Gunakan HTTPS untuk API nyata, dan jangan menonaktifkan pemeriksaan sertifikat hanya agar request berhasil.

// Contoh pemanggilan memakai package:http (pasang package sebelum menjalankan).
import 'dart:convert';
import 'package:http/http.dart' as http;

Future<List<dynamic>> fetchItems(Uri url, String token) async {
  final response = await http.get(url, headers: {
    'Accept': 'application/json',
    'Authorization': 'Bearer $token',
  }).timeout(const Duration(seconds: 10));
  if (response.statusCode == 401) {
    throw StateError('Sesi berakhir, silakan login lagi');
  }
  if (response.statusCode != 200) {
    throw StateError('Server gagal: ${response.statusCode}');
  }
  final decoded = jsonDecode(response.body);
  if (decoded is! Map || decoded['data'] is! List) {
    throw const FormatException('Format respons API tidak sesuai');
  }
  return decoded['data'] as List<dynamic>;
}

Contoh hanya service sederhana, belum production-ready: seharusnya service dipisahkan dari domain model, token diambil dari secure storage melalui dependency, schema data item divalidasi per field, HTTP client ditutup/dikelola, error dipetakan menjadi jenis yang jelas, dan pengujian menggunakan fake client. Untuk data list besar, tangani pagination.

Praktik: panggil API daftar dan tambah item, beri indikator sinkronisasi, implementasikan refresh. Saat offline, tampilkan daftar terakhir yang valid (jika disimpan) dan tanda waktu sinkronisasi. Tes keluar: ketika API memberi 401, UI tidak diam-diam menampilkan data milik akun sebelumnya.

30. Offline-first, konflik sinkronisasi, dan keamanan perangkat

Offline-first bukan hanya men-cache halaman: definisikan data apa yang dapat dibaca offline, operasi yang boleh diantre, model identitas perubahan, waktu perangkat vs server, resolusi konflik, dan mekanisme retry. Gunakan penyimpanan lokal yang sesuai (misalnya SQLite atau solusi penyimpanan terstruktur lain) untuk data item. Token gunakan secure storage platform bila sesuai. Informasikan data yang belum tersinkron, jangan mengklaim sinkron berhasil hanya karena disimpan lokal.

Strategi awal aman: operasi baca menggunakan cache terakhir; operasi tulis online-only dulu. Setelah sistem stabil, tambahkan outbox queue lokal untuk create/update yang idempotent, identitas request unik, versi record (updated_at/version), dan kebijakan konflik eksplisit. Untuk catatan pribadi pengguna, strategi last-write-wins mungkin dapat diterima jika diberi peringatan; untuk stok/presensi/transaksi yang kritis, butuh kontrol konkurensi kuat. Jangan menganggap timestamp device selalu benar.

Praktik: buat daftar status koneksi, waktu sinkron terakhir, dan skenario konflik (edit sama pada dua perangkat). Tulis kebijakan konflik dalam satu paragraf yang bisa dimengerti pengguna. Tes keluar: tidak terjadi silent data loss saat dua perubahan saling bertentangan.

31. Testing Flutter, release, dan operasional

Unit test: aturan bisnis dan ViewModel; widget test: tampilan dan interaksi widget dalam lingkungan terisolasi; integration test: alur aplikasi yang berjalan pada perangkat/emulator. Gunakan flutter analyze, dart format, flutter test, dan periksa accessibility/semantics. Bangun Android/iOS melalui panduan resmi yang sesuai SDK dan target platform; signing key adalah rahasia yang tidak boleh di-commit. Periksa izin aplikasi minimal, ukuran APK, network security config, privacy policy, dan crash reporting sesuai kebutuhan.

Praktik: test jumlah 0 ditolak, loading berubah menjadi hasil, empty state benar, tapping Simpan memanggil repository satu kali. Di perangkat, uji mode pesawat, rotasi layar, font besar, penolakan izin, dan jaringan lambat. Tes keluar: ada checklist rilis dan prosedur menaikkan versi tanpa kehilangan data lokal.
